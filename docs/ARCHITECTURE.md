# Implementation notes

## V2 offline scan milestone

The `feature/offline-scan-inbox` branch is version 2.0.0-alpha.2. Forms generated by
PDFKit include vector QR codes, four widely spaced alignment marks, and an
immutable `PaperForm` template with page coordinates and fixture participants.
Replaced templates remain available as provenance; only current score documents
can approve results. See [offline usage and limitations](V2-OFFLINE.md).

The renderer rasterizes imported PDFs with bundled PDF.js. A dedicated worker
decodes QR codes with jsQR, locates corner marks, fits a page homography, isolates
digit boxes and runs a vendored MNIST-12 model through single-threaded ONNX Runtime
WASM. The model file is checked against a pinned SHA-256 during builds. All runtime
assets are bundled. CSP permits local WASM compilation and local workers but keeps
network requests limited to the application origin. Handwritten free text is not
claimed as recognised; registration levels use local checkbox detection.

The main process owns file selection, source hashes, original images, serialized
scan mutations and approvals. It bounds input sizes and pages, validates payloads,
and checks active tournament/revision. Source and normalized images are stored
under `scans/`, with metadata in the checksummed tournament snapshot. Import is
resumable by source/page/form identity. Human review produces existing domain
commands; a complete approved sheet commits in one store revision. Conflicting
results require the existing explicit correction workflow. Original source hashes
are checked before analysis. Scans are not an alternate route around sporting
validation or downstream protection.

Scan data is an additive format 2. V2 accepts formats 1/2; v1 rejects format 2,
preventing accidental loss by an older writer. Version 1.3 release files remain
available. Opening older group/match packages regenerates their forms, so testing
should use a full copy. A JSON restoration copies scan assets when their original
package is present; pending old-identity sheets become historical ignored scans.

Alpha.2 uses compact 14×18-point digit boxes in the bottom-right corner of score
cells, leaving room for referee tally marks. `src/scan/digits.ts` normalizes local
contrast, removes specks, preserves additional lower ink when a digit touches the
crop edge, centers mass, and compares three input preparations. Weak/disagreeing
reads remain `?` with alternatives; volleyball rules flag invalid pairs but never
choose a digit. Runtime/model failures preserve the aligned page for manual entry.
`geometry.digitTensor` retains the alpha.1 baseline for reproducible comparisons.

Templates snapshot an independent sporting fixture key. Before a layout refresh,
valid legacy templates are certified from their current document associations.
Their original geometry remains usable after a layout-only replacement; changed
participants, targets, IDs or phases remain rejected. This is compatibility with
old paper, not permission to reinterpret an obsolete sporting fixture.

Original recognition values are stored separately from editable review drafts.
Exports include only approved score crops and labels, their digit coordinates,
source grouping hashes and traceable original suggestions. Unaligned/manual page
associations are excluded. Legacy predictions without immutable provenance are
marked unknown. The export never trains a model automatically. Development tools
compare the baseline/new reader on synthetic MNIST conditions or a reviewed local
export, reporting numeric errors and explicit review coverage separately.

This is an independent implementation. No previous application source, orchestration framework or database layout was reused. Version 1.2 uses the icon explicitly supplied by the project owner.

## Stack and tradeoffs

Electron supplies a self-contained desktop runtime, native directory dialogs and printing. React/TypeScript support a responsive French interface and shared typed domain model. PDFKit produces vector A4 sheets with embedded redistributable fonts. Vite builds the renderer, Vitest checks business/persistence/document behavior, and Playwright exercises the real Electron application.

A browser-only implementation would make portable packages, native directory selection and printer integration less direct. A compiled native UI could yield a smaller binary but would require more bespoke work for responsive bracket interaction. Electron trades executable size and memory usage for straightforward distribution and UI maintainability.

## Boundaries

- `src/domain`: types, runtime package schemas, pure command transitions, ranking, scheduling, qualification, bracket dependencies and invariants.
- `electron/store.ts`: validated packages, session locks, SHA-256 envelopes, revision snapshots and atomic writes.
- `electron/pdf.ts`: A4 match/group layout and a source fingerprint excluding scores; `pdf-base.ts` shares branding and fonts; `registration-pdf.ts` renders blank/filled rosters.
- `electron/main.ts`: serialized commands, ID/revision checks, native dialogs, document-before-confirmation commit, printing and restoration.
- `electron/preload.ts`: narrow message bridge. Renderer Node integration is off, context isolation and sandboxing are enabled, content is bundled and loaded through a restricted protocol, and IPC senders are checked. See [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security).
- `src/ui`: registration, progression, phase preparation/scoring, bracket, documents and audit. Sporting policy lives in the domain rather than the widgets.

## Durable packages

Each `.openvolley` folder has `tournament.json`, `tournament.backup.json`, `history/revision-N.json`, `documents/*.pdf`, and a temporary live-session lock.

For a modest single-operator aggregate, versioned JSON snapshots avoid native database builds while retaining complete transaction semantics. A command clones its input and validates the complete new state. Writes use an exclusive temporary file, flush, close and atomic rename. The old revision/backup are persisted before current-state replacement. Failure leaves the in-memory authoritative revision unchanged. PDFs are generated first, then associated with the confirmed phase in a single tournament commit. A failed operation can leave an unreferenced PDF, but cannot leave a half-confirmed phase.

SHA-256 detects accidental modification, not malicious tampering. Runtime schemas and domain invariants remain necessary. Invalid candidates never replace the active session. The desktop queue finishes old saves before switching, and every mutation includes package ID and expected revision. Invalid UI edits must be resolved or deliberately abandoned. This is a single-writer local store, not a shared concurrent database.

## Progression and correction

Immutable UUIDs identify all entities. Confirmed phases snapshot names, strength and rules. Nodes follow source dependencies independently within each branch, never timestamps or incidental IDs. A final is one phase with internal rounds.

Knockout slots reference registered teams or upstream winner/loser outcomes. Topological recalculation derives participants and exemptions. Corrections identify affected results/phases, require explicit consent, archive the prior situation and invalidate dependencies. Group corrections conservatively invalidate all descendants and relevant split; restoration creates a distinct package.

## Version 1.1 compatibility

Optional additive schema fields retain schema 1 readability: embedded normalized PNG branding, website, previous-rank snapshots, document kinds/fingerprints and a per-result scored margin. Historical phase rules remain available to validate existing scores. Every new result records a two-point margin, including a correction inside a former one-point phase. Ranking always compares exact wins/played and difference/played products. Subsequent groups allocate ranked teams in alternating snake bands and request named decisions only when a tie spans different group destinations.

Opening a tournament refreshes outdated/missing phase sheets before adopting the session. Creating a final prepares all sheets, including unresolved fixtures. Advancing or correcting participants refreshes their fingerprints and PDF associations in the same tournament revision. Unchanged sheets are reused. The logo is embedded in JSON rather than linked to the source file.

## Bracket draw overrides

New knockout phases snapshot the source group phase’s general ranks, independent of seed or draw position; older brackets derive ranks from their source on display. The bracket-swap command validates an unplayed knockout and two registered first-round team references, exchanges only those reference IDs, then runs the existing dependency recalculation. It invalidates PDFs whose participants/byes changed; desktop generation writes refreshed associations in the same saved revision. The original seed order, qualification, rank snapshot and graph IDs remain intact. Any result/forfeit locks further draw swaps for that phase. UI edit mode provides two accessible team-selection buttons per first-round match without nesting them inside match buttons.

## Reliable printing

The Electron PDF viewer is no longer used as the print target. A second Vite entry point bundles PDF.js and its worker offline. A sandboxed window receives only the selected PDF through a sender-scoped preload channel, renders pages sequentially at 200 DPI, waits for image decoding/fonts/layout, and reports readiness. The main process then prints A4 HTML pages with explicit zero page margins. Preparation has a timeout, and failure/cancellation closes its window and releases the operation. The source PDF stays vector-based for Afficher. Tests intercept only the hardware print call, capture actual Chromium printToPDF output, and verify nonblank decoded images and PDF content resources on every page.

The print renderer has a restrictive CSP and no tournament command bridge. Window IDs bind transient PDF jobs; job data is removed as soon as preparation settles.

## Distribution and verification

The portable Windows x64 executable bundles the runtime and user-supplied volleyball icon. Operators do not install Node.js. macOS/Linux packages are not validated. Tests use only temporary data. PDF tests parse actual page counts/A4 sizes; representative pages are also rasterized and visually reviewed. Native directory selections are stubbed in repeatable GUI tests, and physical printing is a manual hardware check.
